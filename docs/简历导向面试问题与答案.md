# hmdp-plus：简历导向面试问题与参考回答

整理日期：2026-11-09。面试官只看到项目介绍和简历亮点，不预设他阅读过源码。每题从业务动机、方案和取舍展开，基础知识融入回答，分类放在题目末尾。追问沿回答中提及的细节深入。

这是在开源教学项目基础上的学习与本地适配。Kafka、分片、限流等主要实现来自上游；个人贡献要按实际修改和实测讲述，不直接说成从零设计，也不使用未经实测的性能数字。

## 一、整体表达

### 1. 介绍一下项目，它比原来的黑马点评增加了什么？（项目表达-业务与架构）

它保留了本地生活点评和优惠券抢购的业务，但重点从“用 Redis 实现功能”扩展到了抢购入口控制、热点访问、消息处理和失败恢复。用户抢购前需要短时通行令牌，并受到限流；券详情增加本地缓存，订单改由 Kafka 异步落库，同时记录库存轨迹和对账信息。

数据侧也从单库单表变成了分库分表，前端升级为 Vue 3。我的理解是，这些改动增加了可扩展能力，同时也增加了缓存失效、跨系统补偿和分片事务的复杂度，所以不能只把它介绍成“中间件更多”。

**追问：你认为最有价值的升级是什么？**

我会选失败过程能被追踪和恢复。原来只看库存和订单最终值，出现差异很难判断请求是否还在处理中；新增轨迹和对账以后，有条件按订单身份分析过程。不过有这些记录不代表所有故障已经验证，仍需要针对重复和迟到消息实验。

### 2. 这是开源项目，你个人做了哪些工作？（项目表达-个人贡献）

架构和主要业务来自上游，我做的是在本机准备隔离环境、整理构建与启动流程、处理实际遇到的兼容问题，并核查原版到 Plus 的调用链变化。功能和测试结果以本地验收记录为准，不把源码里出现的能力全部当成自己实现的成果。

整理过程中我也会对照 README 和实际入口，例如是否真的启用了某种缓存、对账是否有调度，以及消息失败后具体做了什么。这些核对决定了简历能写到哪个程度。

**追问：为什么还需要对照入口，代码存在不就能写吗？**

代码可能是旧方案、备用实现或未启用分支。简历写“使用某方案完成某功能”，应能说明请求实际经过哪里。知道一个类存在，与知道业务在使用它，是不同的。

## 二、入口控制

### 3. 已经登录了，为什么抢购还要领取令牌？（redis-原子校验；系统设计-准入控制）

登录解决身份，抢购令牌约束的是这个用户对这张券的一次短时入口资格。把两者分开，可以在真正进入库存逻辑之前过滤过期、重复或不合规的请求，而不是让所有已登录请求直接竞争库存。

当前令牌与用户和券关联，短时间有效，并通过 Lua 比较后消费，避免同一令牌在并发下反复使用。但拿到令牌并没有预定库存，用户仍可能在后续抢购时遇到售罄。

**追问：领了令牌就保证能抢到吗？**

不保证。令牌是通行凭证，库存资格仍由后面的原子扣减决定。如果业务要做到领令牌即锁名额，就需要把名额预占、超时释放也一起设计，那是不同的业务承诺。

### 4. 限流放在哪里，为什么同时限制 IP 和用户？（redis-限流；系统设计-流量治理）

项目分别在领令牌和实际抢购时执行限流，避免只保护其中一个接口，另一个被大量请求拖慢。用户维度限制个人频繁重试，IP 维度补充约束同一来源的集中请求，两者都不能单独代表真实访问者。

当前有令牌桶和可选滑动窗口实现，还提供白名单与扩展策略。共享网络下很多用户可能共用 IP，所以阈值必须结合场景配置，不能简单把同 IP 都当成攻击。

**追问：为什么选令牌桶，不直接固定窗口计数？**

令牌桶按速率补充令牌，桶容量允许有限突发；固定窗口实现简单，但窗口交界处可能短时间放行两段额度。滑动窗口能更细地约束时间范围，但记录和计算成本更高。选型要围绕允许的突发量和实现成本，不能把算法名字当成效果证明。

### 5. 限流和防重复提交有什么区别？（系统设计-流控与幂等）

限流回答一定时间内允许多少请求进入，即使请求全都合法，也可能因为总量过大需要限制。防重复提交回答的是同一个业务请求重试时，能不能重复产生效果。

因此项目有入口频控、一次性令牌，以及消费端去重和业务判重，它们分别保护不同阶段。入口挡住重复请求有助于减少压力，但不能代替消息重放时的幂等。

**追问：用户因为限流失败重试，会不会消耗购买资格？**

要看执行顺序和接口承诺。应尽可能在预占之前完成频控，避免失败请求先扣名额；令牌已消费但抢购失败时，用户如何重新领令牌也要定义清楚，不能把网络重试和永久失去资格混为一谈。

## 三、缓存与数据

### 6. 有 Redis 了，为什么还增加本地缓存？（redis-多级缓存；java-Caffeine）

热门券详情可能被每个抢购请求读取，即使 Redis 很快，重复网络往返和热点 key 访问也会集中到它。Caffeine 把一部分详情放在进程内，优先本地命中，再查 Redis，最后回源数据库。

本地缓存适合相对稳定的券信息，不能把每个实例里的库存副本当成最终扣减依据。这里缓存详情和原子库存是分开处理的。多了一层副本，也就多了一层失效问题。

**追问：修改券信息后，其他实例的本地缓存怎么办？**

源码通过 Kafka 失效事件通知各实例，各实例使用独立消费组接收。还要考虑掉线、重启、消费起点和事件发送失败，因此需要失效重试与最大陈旧时间，不能认为发了一条消息就已经强一致。

### 7. 布隆过滤器、空值缓存和双重检查为什么一起用？（redis-缓存穿透与击穿）

它们针对的问题不同。布隆过滤器先拦截明确不存在的 ID，空值标记减少可能误判或已删除数据的重复回源，重建锁控制热点失效时并发查库。

拿到锁后还要再检查缓存，因为等待期间前一个请求可能已经完成回填。否则后面的请求虽然排队拿锁，仍然会逐个查询数据库，锁只把重复工作串行化了，并没有消除它。

**追问：布隆过滤器已经说存在，为什么数据库还是查不到？**

布隆过滤器允许误判，新增、删除与过滤器维护也可能存在时间差。它只回答可能存在，不返回业务数据，因此还需要查缓存和数据库，并正确处理空结果。

### 8. 增加缓存后，一致性怎么处理？（redis-缓存一致性；mq-失效事件）

先区分数据类型。详情可以按业务容忍短暂陈旧，库存扣减则不能依赖各实例的旧副本。项目在券更新时清理缓存并发送失效事件，在读取时按详情缓存和库存加载分别处理。

失效事件把一次修改传播到多个实例，但数据库更新、Redis 删除和 Kafka 发送不是天然同一事务。应按故障窗口考虑重试、版本和对账，不能因为用了读写锁就认为跨系统全部原子。

**追问：缓存失效消息如果比后面的修改更晚到，会怎样？**

删除型事件通常会造成额外回源，而带旧值回填的事件可能直接覆盖新数据。需要明确事件语义，必要时带数据版本并拒绝旧版本写入，同时考虑乱序与重复。

### 9. 为什么要分库分表，按什么维度分？（mysql-分片与路由）

上游把用户、券、订单和日志等表按业务字段配置到两个库、多张物理表中，用于学习数据量扩大后的路由和查询设计。用户查询与订单查询的访问方式不同，所以不能把所有表都机械地按同一个字段拆。

订单按用户和券定位后，按订单 ID 查单未必知道目标分片，因此新增订单路由记录。分片让写入和存储可以分散，但也让缺少分片键的查询、关联和事务更复杂。

**追问：分库以后，一张热门券的库存竞争也解决了吗？**

不一定。大家更新的仍可能是同一张券对应的那一条库存记录。分片分散了不同业务数据，不会自动把单个热点资源变成多个独立资源。是否需要分段库存，要再考虑分配和一致性成本。

### 10. 分库后，事务注解还能保证所有写入一起回滚吗？（spring-事务；分布式-跨库一致性）

不能仅凭注解下结论。订单、库存、路由和对账日志可能按不同键落到不同库，普通本地事务的保护范围必须结合实际数据源和 ShardingSphere 事务模式确认。

本地两个库仍然在一台 MySQL 上，也不等于已经验证跨节点故障。可以选择让需要原子的业务共置、使用适合的分布式事务，或者通过状态和补偿实现最终一致，但都要说明代价。

**追问：为什么不直接全部用分布式事务？**

它会增加协调、连接占用和故障恢复成本，也不能自动把 Redis 和 Kafka 的所有副作用纳入同一个边界。应先明确不变量和必须原子的范围，再决定是否值得采用。

## 四、消息与失败恢复

### 11. 为什么从 Redis Stream 换到 Kafka？（mq-选型与消费模型）

Plus 把订单消息、缓存失效等事件放到独立的 Kafka 系统里，结合生产确认、消费确认和处理回调组织消息链路。这样可以更明确地管理不同事件和消费者，但也增加了一个依赖。

不能简单说 Kafka 一定更快或更可靠。原版 Lua 可以在 Redis 内同时预扣并 XADD；现在是 Redis 预扣完成后应用再发送 Kafka，中间反而多了跨系统窗口，所以必须连同失败回调和对账一起解释。

**追问：Redis 扣了库存，进程在发送 Kafka 前崩溃，怎么办？**

发送失败回调未必有机会执行，因此需要通过持久化受理记录、预占轨迹或恢复扫描发现这类中断。当前轨迹和对账为调查提供信息，但还需验证具体丢失窗口，不能只说有回调就能覆盖进程突然退出。

### 12. Kafka 的生产幂等和业务幂等有什么区别？（mq-生产幂等；分布式-业务幂等）

生产幂等用于减少生产者协议重试造成的重复日志记录；业务幂等关注的是同一业务事件反复处理后，是否多建订单、多扣库存或重复返还。两者保护范围不同。

项目配置了生产幂等，并在消费建单方法中按消息身份做防重复执行，同时查询业务订单。数据库约束、事务和去重记录的有效期仍需要一起考虑，不能把消息系统的配置当成业务正确性的替代。

**追问：同一个业务重新发送时，生成了新的消息 UUID，还能去重吗？**

仅按 UUID 就识别不了，因为它看起来是新消息。要有稳定的业务标识，并明确同一订单、同一购买资格的约束，尤其不能只保证消费方法少执行一次，却忽略库存和补偿的副作用。

### 13. 数据库已经建单，但消费确认失败会怎样？（mq-确认与重复消费）

消息可能再次交给消费者，所以数据库提交应先于确认，而消费逻辑需要识别已经完成的业务。先确认再写库，崩溃后反而可能没有重试入口。

本项目消费失败还会进入 Redis 返还路径，因此重投与已存在订单的处理要特别核查。不能把所有异常都当成同一种“订单没成功”，否则可能把已经成交的库存返还出去。

**追问：如何判断该补偿还是该当作重复成功？**

结合订单身份、数据库终态和对应预占记录判断。已成功业务应按幂等结果处理，明确失败才能补偿；未知状态先查明或保持可恢复状态，不能只靠 catch 到异常就返库存。

### 14. 为什么消息消费延迟太大时要做特殊处理？（mq-消费延迟；系统设计-受理语义）

源码对延迟超过十秒的下单消息有预占返还分支，体现的是这版教学实现对等待时长的业务选择：不能让用户一直拿着一个没有进展的受理结果。

但十秒不是普适阈值。网络抖动或积压也可能让正常请求变慢，判断终态时必须考虑同一订单是否已经完成，以及返还是否会被重复执行。对外承诺也应明确是排队受理，还是限定时长完成。

**追问：多等一会儿可能成功，为什么不一直重试？**

无限等待会占住名额、增加积压，并让用户无法判断结果。应根据业务承诺区分可重试与终态失败，给重试设上限，再安全补偿；阈值需要用实际耗时和容量数据评估。

### 15. 库存轨迹和对账日志解决什么问题？（分布式-对账与可追踪性）

只比较 Redis 和数据库的两个库存值，无法知道差异是正常排队还是处理失败。轨迹把订单、用户、券、时间和变更前后数量关联起来，数据库侧再记录落库和返还等操作，才能按业务过程解释差异。

对账可以据此检查缺失订单、缺失轨迹或异常状态。它帮助发现和修复问题，但日志可能过期或写入失败，因此还需要定义事实来源、保留时间和处理中的时间窗口。

**追问：为什么不能发现库存不同就直接覆盖 Redis？**

已经预占、尚未落库的请求会让两边暂时不同。覆盖会把这些名额重新放出去。对账需要结合有效预占、已售和已补偿状态，避免把正常中间态误当成异常。

### 16. 回滚库存是不是简单加一就行？（redis-Lua；分布式-补偿幂等）

如果每次失败重试都加一，重复补偿会让库存越补越多。返还还关系到购买资格和处理轨迹，必须能识别正在补的是哪一次预占。

项目把 Redis 返还动作封装成脚本和统一处理，并保存相关记录。真正判断是否安全，需要继续检查重复返还、已完成订单和迟到消息的竞争，而不是看到有 rollback 方法就结束分析。

**追问：补偿执行后进程崩溃，再执行会怎样？**

应让补偿动作使用稳定身份，原子判断是否已补偿，再修改库存和资格。跨数据库与 Redis 的补偿状态推进还需恢复和对账，否则一个系统写完、另一个没写完仍会留下窗口。

## 五、业务扩展与工程表达

### 17. 订阅、候补和自动发券增加了什么业务难点？（系统设计-排队与状态竞争）

原版主要是用户主动抢购；Plus 增加订阅和通知，部分路径会在加库存或取消后尝试给订阅者分配资格。系统不再只回答当前请求能否成功，还要决定谁按什么规则获得新释放的名额。

候补需要稳定顺序、资格过滤和重复分配防护，不能先取一个人再无条件减库存，因为同时还有主动抢购。当前实现的自动发券路径也需要与主库存规则一致。

**追问：候补第一位不满足会员条件，是直接阻塞后面的人吗？**

要先确定业务规则，可以跳过不合格者，也可以保留某些用户的等待资格，但需定义扫描边界、状态和通知。不能为了严格按队列顺序而让无效队首永久占住资源。

### 18. 为什么抽出锁、限流、消息等多个模块？（工程设计-模块化与复用）

这些能力会被多个业务入口使用，抽出来能统一参数、异常处理和扩展点，避免每个业务各写一套。业务层更容易表达“这里需要什么约束”，而不是重复 Redis 命令和消息转换。

但 Maven 多模块不等于微服务。当前核心应用仍把这些库加载到一个进程，也不能因为用了注解，就忽略执行顺序、SpEL 参数发现和事务边界。

**追问：抽象越多越好吗？**

不是。只有重复场景和稳定边界足够明确，抽象才有价值。过度包装会让故障定位更难，尤其锁和事务的嵌套必须能追到实际调用顺序。

### 19. 如何证明 Plus 比原版更好？（性能测试-对照实验与正确性）

先定义比较对象和负载。详情缓存可以比较数据库查询量、Redis 操作量和尾延迟；抢购可以比较受理速率、最终落库量、积压和业务成功率；故障恢复则看重复执行、补偿和最终状态是否符合规则。

新旧版本依赖不同，如果硬件、缓存预热和用户模型也不同，就不能把数字差异都归因于升级。本次运行验收是功能证据，只有另行完成对照压测以后，才填写 QPS 和提升比例。

**追问：只看接口响应很快，有什么问题？**

异步接口可能只是更快入队，最终订单却更晚完成。必须同时看端到端完成时间和队列积压，不能把等待从请求线程搬到队列以后，就声称整体处理能力提升。

### 20. 如果继续改造，你会优先做什么？（系统设计-迭代取舍）

我会先把已暴露的正确性边界做实：跨分片事务、订单消息重投与补偿的组合、缓存失效失败和写接口授权。再补可重复的故障实验，用结果决定是否需要调整架构。

上游已经覆盖了很多技术名词，继续堆组件的收益有限。更有价值的是拿一条完整链路，能说明它在失败时怎么走、最后留下什么状态，以及哪些情况还没验证。

**追问：简历里应该突出哪些内容？**
