# hmdp-pro 简历导向面试问题与答案

适用版本：`6efe426`。按「汽车集团车主权益与售后履约平台」的简历表述准备，演示以三家门店、固定一小时的单类工位验证售后预约流程。可先练 1、2、4、5、7、10、12、15 题，再按面试岗位选练。原 Plus 问答见 [Plus 基础问答](hmdp-plus面试问题与答案.md)。

## 一、项目介绍与业务建模

### 1. 介绍一下这个项目，为什么选择保养券预约这个场景？（项目表达-业务建模）

项目从 hmdp-plus 的本地生活购券链路出发。汽车集团发一批保养券后，车主还要在有效期内选网点和工位。实际容易出问题的是改期，用户原本约了 A 网点，新选的 B 网点刚好被抢满，如果先取消 A，用户可能两个网点都约不到。我用独立预约库管理券权益和分时工位，把占用新工位、释放旧工位和变更预约放进一次事务。网点临时停约时，店员还能取消受影响预约并恢复券，车主再选新时段。

**追问：汽车业务都做到什么程度？**

我实现的是适用于这个场景的履约模块，本地用三家门店、固定一小时和单类工位演示。购券、预约、改期、取消和店员核销已经跑通。技师技能、车型对应的不同工时和支付退款还在扩展范围里。这样的范围能让我把改期和核销竞争测清楚。

### 2. 你具体做了哪些，哪些来自开源项目？（项目表达-个人贡献）

门店查询、缓存、抢券令牌、Redis + Lua 预扣、Kafka 异步下单和分片是 Plus 的基础。我主要新增了订单到账后的权益登记、时段容量、跨店改期、停约处置和核销。第一次实现把主动改期和运营邀请放在同一套占位流程，后来拆开了。车主明确选择新时段时一次提交，只有店员发备选邀请才短时占位。为了证明修改有效，我用真实 MySQL 做了并发重放和写入失败回滚测试。

**追问：哪一处最能体现你自己的设计判断？**

主动改期的承诺是用户提交后立刻知道换位是否成功。让用户先占两个工位再确认会增加一个超时状态，还会压缩别人能约的容量。我把换位放进一个本地事务，用预约版本处理旧页面请求，把带超时的占位留给确实需要用户回复的运营场景。

### 3. 为什么抢到券之后还有可能约不到？取消会退库存吗？（领域建模-券权益与履约容量）

集团活动的券库存限制能发多少份权益，预约容量取决于门店和时间。例如车主已经有券，周六上午 A 网点只有一个空工位，满了就得选 B 网点或者别的时间。取消预约归还的是原时段工位，权益恢复可用，仍可持原券再约。交易退款需要撤销券权益，并且要有独立的交易流程。

**追问：原来的优惠券取消接口还能用吗？**

普通券继续走原接口。已配置预约能力的券在该入口被拦住，避免交易侧取消后预约库里的券仍能用。本版提供预约取消和权益恢复，跨库退款需要等预约权益冻结、交易退款和结果确认都建立以后再开放。

## 二、预约、改期与停约

### 4. 两个人同时抢最后一个工位，怎么防止超约？（MySQL-行锁、条件更新与事务）

提交时先锁当前订单的权益行，保证同一张券不会同时创建两份预约。再锁目标时段，校验店和券是否匹配、时段是否开放，用带 `held + booked < capacity` 的 SQL 增加正式占用量。只有更新成功才写预约、权益状态和流水。这些写入在同一预约库事务里。页面上看到的余位只是选择时的快照，提交仍要检查实际余量。

**追问：权益行锁和时段行锁分别保护什么？**

同一份权益上的请求要按顺序处理，因此权益锁保护一券一预约、版本和幂等。不同车主会拿到不同权益锁，但最终会竞争同一时段。时段锁和条件更新负责保证这个工位不会被分给两个车主。

### 5. 用户从 A 店改到 B 店，怎么做到失败时原预约还在？（MySQL-本地事务与锁顺序；接口设计-版本校验）

客户端提交目标时段和当前预约版本。事务先锁权益，再按时段 ID 升序锁相关时段。如果还有待确认邀请，也把该邀请的目标时段纳入同一锁序。校验版本、期限和目标容量后，增加 B 的正式占用、释放 A 的工位，再更新预约位置与版本。如果 B 满了，或写预约记录时出错，所有变更一起回滚。目标满位和换位中途失败都做了 MySQL 回归。

**追问：为什么不能永远先锁旧店、再锁新店？**

两笔预约可能同时做 A 到 B 和 B 到 A。按业务方向加锁时，两个事务可能各占住一个时段，互相等对方。按 ID 固定顺序就能减少这条路径上的循环等待。事务范围也应保持短，查远程接口或发通知放到提交之后。

### 6. 五分钟占位用在什么地方？过期时用户还能继续改期吗？（系统设计-临时占位与过期回收；MySQL-状态竞争）

车主主动选好时段后直接提交换位。五分钟占位给店员主动发出的备选邀请使用，因为这时还在等车主答复。邀请到期时间还受原预约改期截止与目标开场时间约束。到期后定时任务锁权益、校验邀请状态，再释放对应临时占用。车主仍可按当前预约状态重新选择时段。

**追问：过期清理和用户确认恰好同时到，怎么办？**

两条路径先锁同一行权益。确认拿到锁后用数据库时间判断是否过期，清理也只处理仍待确认的原邀请。确认已经成功时，清理不会再扣一次占位。旧邀请的 ID 与版本也不能用来接受后续的新邀请。

### 7. 网点突然停约，用户在产品里怎么办？（业务设计-履约异常；MySQL-分批处理与幂等）

店员先关闭时段，拦住新的预约和核销。用户看到停约状态，可以自行换时段或取消。店员可每批处理至多 100 笔受影响预约，每笔单独加锁，检查它是否还在原时段。取消时释放原名额和未处理邀请，恢复券并保存原因。若店员没处理，时段结束后扫描会兜底。通知目前在预约页展示，适合演示站内流程。

**追问：为什么不直接把所有人自动改到其他店？**

不同车主接受的距离和时间不同，即使系统找到工位，也需要车主确认。我把算法放在运营入口，店员可按需发建议，用户保留自行改期和取消的路径。真实上线还要接主动通知、触达失败转人工及退款，这些是当前版本之外的工作。

### 8. 用户改期后拿着旧凭证到 A 网点，还能核销吗？（业务安全-资源鉴权；MySQL-终态竞争）

核销校验店员权限、当前预约所属网点、预约版本和服务时间窗。改期和核销都先锁同一权益。改期先提交后，旧店看到的版本与归属已经变化，旧请求会被拒绝。如果核销先完成，权益变为已使用，后来的改期也不能推进。完成的预约保留工位占用历史，防止把已经履约的容量当作新的空位。

**追问：并发核销和同一个核销请求重试，返回应该一样吗？**

用不同请求 ID 并发核销，只有一笔能把预约推进到已完成。用同一个请求 ID 重放时，服务检查相同参数并返回已保存结果。客户端拿到两次成功响应也只对应一次有效核销。

## 三、事务、幂等与购券接入

### 9. 为什么把预约放在独立库，交易已经分库分表了吗？（MySQL-事务边界；ShardingSphere-分片路由）

交易侧沿用 Plus，订单按用户分库、按券分表。预约侧一次改期会更新同一份权益和两个网点时段。如果直接按门店分库，普通本地事务就不能覆盖换位全程。所以当前把权益、时段、预约、幂等和流水放在同一物理库。先让换位的原子性清楚可测，交易订单则作为权益来源。

**追问：预约和交易库之间已经有分布式事务了吗？**

预约以真实落库、归属当前用户且状态正常的订单按需登记权益，预约库以订单 ID 唯一。预约内的本地事务不覆盖交易分片。将来要接退款，我会先在预约域冻结权益，再通过可靠事件请求交易退款，按退款单号防重并等待明确终态。

### 10. 你们先查幂等表再插入，并发不会查到同样的空结果吗？（MySQL-锁定读、READ COMMITTED 与唯一索引；接口设计-幂等）

这个查询在业务事务里，而且每条预约命令已经先按订单主键锁住权益行。同一订单的第二个事务会等待，第一个事务将业务写入与幂等结果一起提交后，第二个事务在 READ COMMITTED 下能查到记录。同一操作同一请求 ID 的参数相同就返回保存值，参数不同会拒绝。真实 MySQL 测试里，8 个同键并发请求均返回版本 1，数据库只写一条命令和一条预约流水。

**追问：用 INSERT ON DUPLICATE KEY UPDATE 就能替代权益锁吗？**

当前幂等写入发生在业务动作之后，单改最后一条 INSERT 不能防止前面的重复业务动作。若要用抢占幂等键的方式，应在业务动作前声明执行权并处理结果状态；而不同请求 ID 同时操作同一张券，仍需要权益状态或锁来协调。

### 11. 请求超时怎么重试，幂等记录会一直增长吗？（HTTP-响应不确定性；MySQL-幂等记录生命周期）

服务可能已提交但客户端没收到响应。同一页面操作在响应不确定时复用原请求 ID，已明确成功或收到带错误码的业务拒绝后结束这次重试记录。服务端把参数和返回值持久化，所以即使业务版本已推进，重放同一个命令也能得到原结果。

**追问：可以给幂等记录加个 TTL 吗？**

当前表保留记录，尚未加清理。简单删除会让过期旧命令有机会按新请求执行，尤其是已经取消后重放旧预约。若需要归档，先定义允许重试的时长和过期请求如何拒绝，再按时间索引小批清理。业务流水继续独立保存。

### 12. 为什么不直接沿用抢券的 Redis 预扣和 Kafka？（系统设计-方案取舍；MySQL-热点行；MQ-削峰）

抢券需要快速拦下大量无库存请求，Plus 用 Redis + Lua 做资格检查和预扣，再用 Kafka 异步落单。预约的业务结果涉及新旧工位、权益和状态一起变化，当前选择本地事务来完成换位。再引入 Redis 预扣会多出缓存与数据库之间的失败和补偿窗口。测试也确实看到了数据库的限制，单时段流量集中后写入会排队。

**追问：把预约也接进 MQ 能解决热点吗？**

可以平滑进入数据库的速率，用户要接受等待和异步结果。如果消费者还是更新同一行，数据库提交上限仍受行锁约束。若实际负载超出目标，我会先考虑缩短事务，测分段容量是否有效，同时设计跨段寻找余量、释放回原段和总量核对。

## 四、运营策略与实验结果

### 13. 运营改派为什么不总是选最近的门店？（算法-贪心与容量匹配；MySQL-一致性快照）

最近优先可能把稀缺工位给选择更多的人。甲能去 B 或 C，乙只能去 B，两店各一位。先把甲放到 B，乙就无处可去。我保留最近优先作为基线，用可选项少的车主先选来发邀，并用最大流比较可安排人数。对比使用同一个只读 REPEATABLE READ 快照，算法在读取完成后运行，实际发邀再检查实时容量和版本。

**追问：快照上有空位，发邀请时已经被别人占了怎么办？**

每笔发邀单独开事务重新检查，容量不足时返回冲突。批次会刷新快照再尝试一轮，仍失败的情况交给运营。规划结果、成功占位与最终接受是三个阶段，用户接受之前不能把方案记为成功履约。

### 14. 候选少优先能达到最优吗？最大流具体优化什么？（算法-二分图最大流与增广路径）

候选少优先是启发式。甲可选 X/Y，乙和丙可选 X/Z，三人候选数相同。按顺序先让甲占最近的 X，乙去 Z，丙就没位。最大流通过增广路径把甲挪到 Y，再给丙腾一个可用位。建模中每笔预约流量上限为 1，时段到汇点的容量是剩余名额，因此最大流求的是给定候选图里的最大可安排人数。

**追问：那为什么最大流方案的平均距离反而更长？**

当前目标函数只最大化人数，额外安排的人可能只能去远店。平均距离也只在各策略各自安排成功的人上计算。若业务要求先最大化人数，再在相同人数下减少总距离，应使用最小费用最大流，并定义距离和时间偏离的权重。

### 15. 简历里写了 9,000 笔实验，这个数字怎么来的？（工程验证-可复现对照、指标口径）

稀缺组用固定随机种子生成 30 份快照，每份 300 笔合成预约、100 个候选时段，同一份输入分别跑三种策略。最近优先安排 7,707 笔，可选项少优先 8,094 笔，最大流对照 8,680 笔。对应 85.63%、89.93% 和 96.44%。这个数字衡量的是规划能覆盖多少订单。

**追问：你能说真实改派成功率提升到 96.44% 吗？**

我会把口径说成合成样本上的最大可安排比例。真实改派还取决于实时占位冲突和用户响应。运营实验要另记邀请发出率、接受率和最终核销率。小样例还测了两位用户实际确认换位，但不能据此推断线上接受率。

### 16. 你怎么测出热点行瓶颈，250 请求每秒意味着什么？（性能测试-k6、P95 与有效吞吐；MySQL-锁等待）

提前准备不同订单权益，用固定到达率单测预约接口，分成单时段和 20 时段均匀写入两组。目标 250 请求每秒、跑 20 秒时，单热点成功约 208 笔每秒，成功请求 P95 是 653.25 毫秒，另有 736 次计划迭代未发出。分散组成功约 250 笔每秒，P95 是 27.49 毫秒。另一次采样在单热点 48 次采样中有 47 次观测到时段锁等待。这些是同一代码在不同流量分布下的本机结果。

**追问：单热点组错误为零，为什么不能说压测通过？**

错误为零只统计已发出的请求。单热点组到达率没维持住，k6 有 736 次未发出，零丢迭代阈值没通过。还要看响应体区分真正成功和满位拒绝，因为接口可能用 HTTP 200 返回业务失败。这个实验用来定位热点，不能当成全链路吞吐上限。

## 五、回归与后续演进

### 17. 怎么验证改期的两个工位真的会一起回滚？（测试-JUnit、真实 MySQL 与故障注入；Spring-事务）

我在 MySQL 预约表加临时测试触发器，让更新预约记录时抛出异常。此时业务已经尝试增加目标工位并释放原工位。如果事务边界不对，表中就会留下名额差异。断言失败后原工位仍占用、目标工位未占用、没有已提交的幂等成功记录。撤除触发器后用同一个请求 ID 重试，换位可以成功。当前仓库共有 10 项回归，8 项涉及真实 MySQL，另 2 项验证规划器。

**追问：为什么还有一套 Node 冒烟？**

JUnit 用真实预约库验证并发和回滚，测试失败时能快速定位到具体规则。Node 冒烟从真实购券和 Kafka 落库开始，继续经过预约 API、改期和店员核销，验证集成入口与最终数据。k6 另外用于观测预约接口的性能。

### 18. 如果实际门店有不同技师、设备和服务时长，你怎么做？（系统设计-多资源排班；MySQL-索引与分页）

首版按固定一小时和同质工位记容量，候选查询最多返回 300 个时段。真实保养可能同时需要合格技师、举升机和连续的服务时间，我会先把服务需求和资源可用日历建出来，再用固定粒度时间片验证连续可用。提交时统一锁定所需资源和时间片，缺任意一个就整体回滚。查询先按网点、车型适配和时间窗缩小候选，再做游标分页。

**追问：什么时候做 Redis、分段容量或分库？**

先确认瓶颈来自候选扫描、锁等待还是连接池。时段数据多可以先缩小查询范围和优化索引；少数热点行再验证分段容量。跨库会增加跨店换位的事务成本，因此我会先用同一工作负载对照，再决定是否值得承担额外的一致性复杂度。
