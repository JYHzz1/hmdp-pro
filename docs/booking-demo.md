# 预约履约演示和验收

## 在浏览器演示

1. 启动 Pro 并设置 `DB_PASSWORD`，运行 `node scripts/smoke-booking.mjs --demo`。记录输出的服务券 ID、三种用户手机号及 A/B/C 时段编号。手机号为本地演示账号。
2. 打开 `http://127.0.0.1:5176/register`，用两位持券用户分别进行手机号快捷登录。点击发送验证码后本地页面会填入模拟验证码。可用不同浏览器会话区分账号。
3. 打开 `http://127.0.0.1:5176/booking`，输入相同服务券 ID，两人都预约 A。选择灵活用户保存距离 6 公里、时间范围前后 4 小时，受限用户保存 2 公里、4 小时。
4. 用门店操作员登录，在预约页输入 A 的时段编号并停约，点击比较改派策略。最近优先可安排一位，可选项少优先和最大流各可安排两位。发送备选方案仍采用可选项少优先，两位持券用户刷新各自预约并确认，原 A 工位随各自确认释放。
5. 到店核销使用当前门店 ID、订单 ID 和预约版本。演示时段是次日 10 点。自动验收脚本在隔离库内调整测试时段，检查核销时间窗。

## 技术取舍

- 预约服务用独立 JDBC 连接池与本地事务。写事务使用 READ COMMITTED，先锁权益主键，再按时段主键顺序加锁，后续查询能读取已提交的当前状态。改派对比用一个 REPEATABLE READ 只读事务构造容量与预约快照。
- 购券订单、券库存与预约容量属于不同业务。业务主键确保每笔订单只登记一次预约权益。预约券暂停沿用原交易取消入口，等待后续接入退款状态机。
- 改派计算不持有写锁。发出邀请时重新校验状态、候选范围和容量。如果用户已预约其他时段，当前改派不会覆盖对方结果。目标余量发生变化时，使用新快照再尝试一轮。
- 五分钟占位由数据库到期时间和定时任务维护。服务重新启动后仍可扫描待处理行。处理顺序和状态检查可防止重复释放。保留原预约仅适用于原时段可履约的情况，停业后原记录作为改派依据。
- 直线距离以原门店为参考点。策略基线按订单顺序选择最近可用店，另一策略优先处理候选较少的用户。两者均为贪心策略。当前样例用于观察可安排比例与额外距离。

## 本地验收

使用 JDK 17、MySQL 8、Redis 和 Kafka 启动后端，Vue 构建通过。执行 `node scripts/smoke-booking.mjs`，验证以下行为：

- 实际 Kafka 订单到账后登记预约权益，拒绝其他用户读取预约及未经授权的门店停约。
- 两个用户争最后一个工位，仅一个预约成功。取消重放后名额只释放一次，可持同一张券再次预约。
- 过期占位由定时任务释放，旧预约保留。旧确认请求不会影响新占位。
- 同一容量快照中最近优先分配 1/2，可选项少优先分配 2/2。两位用户都确认后，原店 booked 为 0，两家新店各为 1。
- 已改期订单在旧店核销失败。同一笔预约用不同请求 ID 并发核销，最终只有一次成功。按时段核对正式预约与临时占位计数。

本轮验证覆盖构建与业务链路，未进行多节点故障、生产吞吐和真实支付测试。
