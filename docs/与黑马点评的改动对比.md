# hmdp-plus 相对黑马点评做了什么改动

核查日期：2026-11-09。上游：java-up-up/hmdp-plus，源码版本 03594d190275a32d151e5d8b45da24c0f4efbe14。本地目标仓库：JYHzz1/hmdp-plus。

本文根据当前可执行入口和源码整理，不能把 README 的宣传描述直接理解为所有故障都已解决。运行实测范围另见《本地构建与验收》。新增架构主要来自上游，本次工作是本地环境适配、运行检查和学习材料整理。

## 先看总体变化

原版主要用 Redis 的不同数据结构实现登录、商铺缓存和秒杀；Plus 保留业务主题，围绕抢购前的流量控制、抢购中的缓存与库存、抢购后的消息恢复和运营扩展重新组织了代码。

|---|---|---|---|
| Java / Spring | Java 8、Boot 2.3 | Java 17、Boot 3.5.4，Jakarta API | 根 pom.xml |
| 工程结构 | 单后端模块 | Maven 多模块，独立封装锁、缓存、限流、消息、分片、ID | 根 modules 配置 |

| 限流 | 没有完整入口流控 | IP/用户维度，令牌桶与可选滑动窗口、白名单、可扩展惩罚策略 | RedisRateLimitHandler |

## 为什么这些变化有价值

### 1. 从“所有人来扣库存”到“先控制谁能进来”

登录表示用户身份，抢购通行令牌表示这次券活动的入口凭证，两者不能混为一谈。控制器会在领令牌和实际抢购两个场景调用限流，再消费短时令牌。令牌本身不保证买到券，库存和重复购买仍由后续逻辑决定。

默认通行令牌启用、有效期 30 秒；滑动窗口开关默认关闭，限流处理可走令牌桶。不能看到代码里有多种算法，就说它们全部同时开启。

### 2. 从“有缓存”到“针对热点与无效请求分别处理”

商铺活跃入口改用布隆过滤、空值标记和锁内二次检查：不存在的数据尽早拦截，并发重建时避免重复回源。券详情进一步加入进程内 Caffeine，减少热点详情的 Redis 往返。

本地缓存也带来多实例失效问题。源码用 Kafka 缓存失效事件，各实例独立消费组接收；随机组名、启动位点、实例掉线后的恢复和最大陈旧时间，仍需结合部署验证。不能把多级缓存直接等同于强一致。

### 3. 从 Stream 直接入队改为 Kafka，并补充失败处理

原版 Lua 将资格修改和 XADD 放在 Redis 的同一次执行里；Plus 的 Lua 写库存、用户资格和轨迹，之后由 Java 发送 Kafka。新方案增加独立消息系统及发送回调、消费回调、对账能力，同时也引入 Redis 成功后、Kafka 尚未确认之间的跨系统窗口。

生产者 acks=all、幂等发送配置和重试，不等于 Redis/MySQL/Kafka 之间恰好一次。当前消费失败会触发预占返还再传播异常，必须进一步检验重投、已存在订单和补偿防重之间的组合行为。

缓存失效链路有专门的 DLQ 消费类；不能据此概括“所有订单消息都配置了同样完整的死信闭环”。

### 4. 从一个库存数字到可追踪的业务过程

轨迹里记录 orderId、traceId、用户、券、扣减前后数量和时间，便于关联 Redis 与数据库日志。对账逻辑会检查未匹配订单或缺失轨迹，并按规则修复或标记异常。

当前对账有控制器触发入口，已读代码中没有发现这个服务方法本身带定时调度。因此应说“有对账执行逻辑和触发接口”，不能仅凭服务名称称其已自动周期运行。

### 5. 分库分表带来新的查询和事务要求

原来一张订单表可以直接按订单 ID 查；按用户和券分片后，单凭订单 ID 未必能确定目标分片，因此新增订单路由信息。用户还增加手机号路由表，减少不知道用户 ID 时的定位问题。

分片不会自动提高单张热门券库存行的并发能力，也不会因为方法上有 @Transactional 就自动获得任意跨库原子性。订单、库存和路由写入可能落不同库，必须核查实际事务模式；本地单机两库测试更不能当作多节点故障验证。

## 当前源码仍须注意的地方

| 内容 | 实际情况 | 面试中如何表述 |
|---|---|---|
| 附近商铺 | queryShopByType 开头把 x、y 置空，活跃路径退回普通列表 | 不声称上游当前已经启用 GEO 距离查询 |
| 订单唯一性 | 提供的分片订单表只有主键，没有 hmdp-lab 那样的用户/券联合唯一键 | 分开解释消息去重、业务判重和最终数据库约束 |
| 分布式事务 | 存在本地事务注解，不能由此推断跨两库完全原子 | 明确验证过的路径，额外研究 XA 等方案的成本 |
| 库存自动补偿 | 有多个回调与对账路径 | 需要重投、乱序、迟到消息、重复补偿实验，不说“绝不超卖、绝不丢单” |
| 初始化 | 启动会清理对应缓存并调整演示券活动时间 | 必须使用隔离演示库与 Redis，不能直接套生产数据 |
| 认证授权 | 验证码接口直接返回验证码，登出仍 TODO，写接口保护较宽 | 这是本地教学系统，不作为生产安全完成品 |
| 支付核销 | 当前控制器有取消和查单，不等于接入真实支付/到店核销 | 不把规划功能写为已实现 |
| 性能宣传 | README 含高并发与完善性描述 | 使用本地报告中的数据，不借用宣传指标 |
